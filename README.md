# 心理健康 AI 服务平台

面向高校场景的心理健康服务系统，服务 **学生 / 辅导员 / 管理员** 三类角色。

核心是一条**由 AI 驱动的服务闭环**：

```
学生对话  →  情绪与风险识别  →  危机自动建单  →  辅导员认领处置  →  留痕可回溯
```

AI 在这里不是「一个聊天功能」，而是一层**贯穿业务的能力**：它检索知识库、
查询情绪历史、推荐自助练习、推送标准化测评、并在判断需要时主动转介人工。
每一步执行都被记录成可回放的轨迹。

| 依赖 | 版本 | 端口 | Windows 上怎么装 | 说明 |

> ⚠️ **三个最容易卡住的坑**（Windows 环境）：
> 1. **Windows 没有官方 Redis**，需用 Memurai 替代；
> 2. **RabbitMQ 依赖 Erlang**，必须先装 Erlang 再装 RabbitMQ；
> 3. **RabbitMQ 是强依赖**，服务没启动应用会直接启动失败。

#### Redis —— Windows 需使用 Memurai

**Redis 官方不提供 Windows 版本**（官方仅支持 Linux/macOS）。在 Windows 上可选：

| 方案 | 说明 |
|---|---|
| **Memurai**（推荐） | Redis 兼容的 Windows 原生实现，装完即作为 Windows 服务自启动，无需 WSL |
| WSL2 | 在 WSL 里跑官方 Redis，适合已用 WSL 的开发者 |
| Docker | `docker run -d -p 6379:6379 redis` |

**Memurai 安装步骤：**

1. 从 [memurai.com/get-memurai](https://www.memurai.com/get-memurai) 下载
   **Developer Edition**（开发用途免费，商业用途需授权）
2. 安装后会自动注册为 Windows 服务并监听 **6379** 端口
3. 验证是否可用：
   ```bash
   memurai-cli ping
   # 返回 PONG 即为正常
   ```

> 本项目的 `application.yml` 默认连接 `localhost:6379`，与 Memurai 默认配置一致，无需额外改动。

#### RabbitMQ —— 必须先装 Erlang

RabbitMQ 是用 Erlang 写的，**装 RabbitMQ 前必须先装 Erlang**，否则安装或启动会失败。

1. 先装 [Erlang/OTP](https://www.erlang.org/downloads)（安装时保持默认选项）
2. 再装 [RabbitMQ Server](https://www.rabbitmq.com/download.html)
3. 开启管理台并启动服务（**需以管理员身份打开命令行**）：
   ```bash
   rabbitmq-plugins enable rabbitmq_management
   net start RabbitMQ
   ```
4. 访问管理台 http://localhost:15672 确认可用（**默认账号密码均为 `guest`**）

服务启动后，本项目所需的消息队列与死信队列会**由应用自动创建**，无需手工建队列。

> **Docker 方式（更简单，且无需装 Erlang）**
> ```bash
> docker run -d --name rabbitmq -p 5672:5672 -p 15672:15672 rabbitmq:management
> ```

默认连接配置为 `localhost:5672`，账号密码 `guest / guest`，可在
`application.yml` 的 `spring.rabbitmq` 下修改，或通过环境变量覆盖。

#### 快速自检环境是否就绪

启动后端前，可先用以下命令确认三个依赖都在监听：

```bash
netstat -ano | findstr "3306 6379 5672"
```

三者都出现 `LISTENING` 即可继续。

## 二、功能与设计说明

### AI 对话

- 流式输出（SSE），前端可**中途停止**，停止时后端会真正中断上游 LLM 调用，
  避免用户已经点了停止、token 却仍在消耗、回复仍被写入数据库。
- 会话记忆用自实现的 `RedisChatMemory`（而非默认内存版），服务重启不丢、多实例可共享，
  并带 30 条滑动窗口与 7 天过期。

### 情绪识别（Structured Output）

对话过程中异步分析用户情绪，结果驱动前端的「情绪花园」（情绪分值、风险等级、治愈建议）。

- 使用 Spring AI 的 `call().entity()` 做**结构化输出**，由 JSON Schema 约束模型返回格式，
  无需手写正则解析自由文本。
- 情绪分析使用**独立的 ChatClient**，不挂记忆 Advisor——否则评估指令会污染用户的对话记忆。
- 结果会做**防御性校验**：越界分值钳制、修正「风险等级高但情绪积极」这类自相矛盾状态。
- 异步执行且全程异常隔离：**分析失败不影响用户聊天**，仅降级为不更新情绪。
- 检测到风险等级 ≥ 2 时打 ERROR 日志（可对接告警）；等级 3 为自伤/自杀倾向。

### 分层会话记忆

单一滑动窗口有个明显缺陷：超出窗口的对话会被**直接丢弃**。用户在第 5 轮说过
「我妈妈最近生病了」，到第 40 轮时 AI 已完全不知情，可能再次追问，让用户觉得
「我说过了你怎么还问」。

因此把记忆分为两层：

```
长期层：chat:summary:{conversationId}   早期对话的 AI 摘要      ← 跨窗口保留
短期层：chat:memory:{conversationId}    最近 30 条完整对话       ← 保留细节与语气
```

- 读取时把摘要作为一条 **SystemMessage 置于最前**，再接上短期窗口的原始消息，
  模型因此既知道早期要点，也能看到近期的完整上下文。
- **滚动更新而非重建**：每次只压缩「旧摘要 + 新溢出内容」。
  若每轮重新摘要全部历史，开销会随对话变长**线性增长**。
- 摘要生成**异步执行**（复用 `aiAnalysisExecutor`）——记忆写入发生在对话主链路上，
  绝不能因调用大模型而拖慢响应。
- 摘要失败时**保留旧摘要不动**：最坏情况是「这段没被记进长期记忆」，
  而不是「记忆全没了」。

> **实测**：预置 32 条消息（第 1 条是「我妈妈生病住院了」），触发溢出后用一句话询问，
> AI 准确复述出该事实。而此时短期窗口内已**完全不含**「妈妈 / 母亲 / 住院」任何字样——
> 也就是说，AI 对这件事的了解 100% 来自长期摘要。

### 安全护栏（受限话题）

对**用药、自我诊断、自伤**三类受限话题，**不允许模型自由生成**，
改用人工撰写、经过审校的固定话术。

> **为什么**：大模型在缺乏依据时会产生「贴心的编造」——面对用药问题可能给出
> 看似专业的药名与剂量。在心理健康场景下，这类编造可能造成真实伤害。

- 识别采用**窄模式匹配**，只在用户明显索取具体建议时命中
  （「吃什么药」命中，「我不想吃药」不命中——后者是正常倾诉，拦截会破坏陪伴感）。
- 命中后**直接返回预置话术**，不调用模型；话术仍写入对话记录与记忆，
  保证会话完整性与下一轮上下文一致。
- **拦截放在情绪分析之后**：即使用户触及受限话题，其情绪与风险仍照常记录，
  否则「我想自杀」这类最该被记录的消息反而不入库。
- 话术统一写得温暖并留出继续对话的入口——生硬的「我不能回答这个问题」本身就是伤害。
- 危机求助渠道（热线、咨询中心）通过配置注入，部署方应改为本地实际可用的资源。

### 危机干预闭环

**改造前的断点**：AI 识别到高危用户后只打一条 ERROR 日志——识别是准的，
但「打完日志就没有下文」：没有人被通知、没有记录、无人跟进。

现在补成完整闭环：

```
风险等级 ≥ 2（或测评风险题项命中）
     ↓
① 写入危机事件 crisis_event（不可变的事实留痕）
② 自动创建工单 crisis_work_order（待认领）
     ↓
③ 辅导员认领（处理中）→ 填写处置结果（已闭环）
     ↓
全程可回溯
```

- **事件与工单分表**：事件回答「发生了什么」（含触发原文、情绪、风险等级），
  写入后不再修改；工单回答「谁在处理」，承载可变的工作流状态。
  合并会导致「改工单状态时连带改写事件记录」，而危机处置最需要可追溯。
- **会话级去重**：同一会话存在未闭环工单时不再重复建单，
  否则用户连说几句高危的话就会刷出一串工单，反而淹没真正紧急的事项。
- **状态单向流转**：待认领 → 处理中 → 已闭环，非法流转在服务层拦截；
  **闭环必须填写处置结果**——只标记「已处理」不写内容，事后无法追溯，等于没有闭环。
- 工单含学生高危对话原文，**仅对辅导员角色开放**，管理员无权访问。

### 工单超时自动升级（RabbitMQ 延迟队列）

工单创建后若无人认领，仅靠「辅导员主动查看列表」是不可靠的——
高危学生可能因为没人看到而错过干预时机。因此用延迟队列实现自动升级：

```
建单 → 投递延迟消息 ──(TTL 到期)──→ 死信交换机 → 检查队列 → 消费者
                                                                ↓
                                          回查工单状态：仍是「待认领」才升级
                                                                ↓
                                          标记 escalated + 通知管理员
```

- **用延迟队列而非定时任务轮询**：轮询需要扫全表判断「哪些超时了」，
  开销随工单量线性增长且有精度损失。延迟消息把「何时该检查」交给中间件，
  到期即触发，无无效扫描。
- **按紧急程度分队列**：RabbitMQ 只从**队首**过期消息——若把 15 分钟和 60 分钟的
  工单混在同一队列，排在队首的长 TTL 消息会阻塞后面短 TTL 消息的过期，
  导致高优先级工单的升级被严重推迟。**每个 TTL 一个队列**是官方推荐解法。
- **消费者回查状态而非直接升级**：消息投递后工单可能已被认领——必须回数据库看最新状态。
  这也让处理天然幂等：重复消费不会造成错误升级。
- **升级标记防重复通知**：延迟消息可能重复投递，没有 `escalated` 标记会导致
  同一条工单反复通知管理员。

> ⚠️ **修改超时配置后必须重建队列**
>
> RabbitMQ 的队列参数（含 TTL）**创建后不可修改**。若改了
> `crisis.timeout.*-seconds` 却不重建队列，应用启动时会报
> `PRECONDITION_FAILED: received '900000' but current is '15000'`，
> 且实际仍按旧 TTL 生效。
>
> **重建步骤（顺序很重要）**：
> ```bash
> # 1. 必须先停止应用——否则运行中的应用会立即重新声明旧队列
> # 2. 再删除队列
> curl -u guest:guest -X DELETE http://localhost:15672/api/queues/%2F/crisis.timeout.high
> curl -u guest:guest -X DELETE http://localhost:15672/api/queues/%2F/crisis.timeout.normal
> curl -u guest:guest -X DELETE http://localhost:15672/api/queues/%2F/crisis.timeout.check
> # 3. 最后启动应用，队列会按新配置重建
> ```

### 通知渠道（站内信 + 邮件）

**为什么需要**：工单创建后若只是躺在数据库里，没人去看就等于没建单。
通知把「有事发生」主动推给该处理的人，闭环才真正成立。

| 渠道 | 作用 | 可靠性 |
|---|---|---|
| **站内信** | 写入 `notification` 表，用户下次打开时可见 | 保证留下记录 |
| **邮件** | 主动触达，适合「人不在系统里」的场景 | 需配置 SMTP |

- 建单后自动通知**全部辅导员**（不指定具体接收人——谁先看到谁处理）；
  超时升级后通知**全部管理员**。
- **邮件可降级**：未配置 `spring.mail.host` 时记录一条 WARN 后跳过，
  **不影响站内信与主业务流程**——这样项目既保留完整邮件能力，
  又不会因为环境缺失而无法运行。
- **通知失败绝不影响主业务**：站内信与邮件都在内部吞掉异常。
  工单已经建好了，若因为发通知抛异常导致建单事务回滚，那才是真正的灾难。
- 前端导航栏有**通知铃铛与未读数**，30 秒轮询一次——
  没有 WebSocket 推送时，轮询是成本最低的兜底手段。

### 受控心理测评（PHQ-9 / GAD-7）

标准化量表作为**受控工具**接入，体现「不确定的能力交给模型，确定的规则交回代码」：

| 角色 | 职责 |
|---|---|
| Agent | **只决定「什么时候该测」** |
| 服务端 | 题目内容 + 计分 + 风险判定 |
| 前端 | 原样渲染题目，不复述、不改写 |

> **为什么题目必须预置、不能让模型生成**：PHQ-9 / GAD-7 是经临床验证的标准化量表，
> 题目措辞、顺序、计分方式都经过研究确定。一旦由模型「用自己的话转述」，
> 量表就失去信效度——测出来的分数没有参考意义。

- 工具描述中明确要求模型**不要在对话中逐题提问或复述题目**，
  只把量表推送到界面，由前端从服务端拉取渲染。
- **风险题项独立于总分判定**：PHQ-9 第 9 题（自伤念头）得分大于 0 即触发危机流程。
  实测总分仅 12 分（中度）时，因该题得 1 分仍准确建单——
  若只看总分阈值，这个信号会被漏掉。
- 计分与严重程度分界写在服务端代码而非配置：它们是临床共识，不应被随意调整。

### Agent 工具编排

AI 不再只是「问答 + 顺带查资料」，而是为达成目标自主编排多个工具：

| 工具 | 能力 | 受控约束 |
|---|---|---|
| `searchKnowledge` | 知识库语义检索 | 检索不到时明确告知，禁止编造 |
| `queryMoodHistory` | 查询用户情绪历史 | **用户身份取自服务端上下文，非模型参数** |
| `recommendPractice` | 推荐自助放松练习 | 练习库预置，模型只选不编 |
| `escalateToHuman` | 主动转介人工 | 建单失败必须如实告知，不得虚假承诺 |
| `triggerAssessment` | 推送标准化量表 | 题目预置，模型不生成内容 |

- **实测的编排行为**：用户说「考试焦虑，怎么缓解」时，Agent 自主执行
  `recommendPractice` → `searchKnowledge` 两步编排（先给方法、再补知识），
  这不是固定链路能实现的。
- `queryMoodHistory` 的 `userId` 来自 `AgentContext`（服务端注入）**而非模型传入的参数**，
  否则模型可能被诱导查询他人的情绪记录。
- `escalateToHuman` 与规则驱动的自动建单**共用同一套去重逻辑**，
  避免出现「规则建了单、Agent 又建一张」。

### Agent 执行轨迹（可观测性）

Agent 与普通问答机器人的区别在于「多步执行」。如果这些步骤不可见，系统就是黑盒——
回复不对时无法判断是**没检索**、**检索错了**、还是**判断失误**。

因此每一步都被记录并可回放：

```
[1] 学生提问   我马上要考试了，特别焦虑，有什么办法能缓解一下吗
[2] 调用工具   recommendPractice("考试焦虑") → 推荐 5-4-3-2-1 着陆法    0ms
[3] 调用工具   searchKnowledge("考试焦虑怎么办") → 命中 3 篇            1110ms
[4] 生成回复   943 字                                                  5215ms
```

- **AOP 切面统一拦截** `@Tool` 方法自动埋点，而非在每个工具里手写记录。
  埋点是横切关注点，写进业务代码一是重复，二是**将来新增工具容易漏掉**——
  而轨迹一旦不完整就失去排查价值。
- 切点用 `@annotation(Tool)` 而非包路径：包路径会随代码结构调整失效，
  「所有 `@Tool` 方法」才是真正想表达的语义。
- **跨线程传递上下文**：工具执行在 Reactor 弹性线程池上（实测为 `boundedElastic-N`），
  与发起请求的 Tomcat 线程不同，**ThreadLocal 取不到值**。
  因此改用 Spring AI 的 `ToolContext`——它随调用链传递，且**对模型不可见**
  （不参与工具签名，已反编译 `MethodToolCallback` 确认）。
- 步骤计数器随 `ToolContext` 创建，每个轮次独立计数，
  无需共享状态、无内存泄漏、多实例部署也不冲突。
- **轨迹记录全程吞异常**：它属于可观测性能力，记录失败最多少一条轨迹；
  若因写库异常导致用户对话中断，就本末倒置了。

### 知识库语义检索（Tool Calling + RAG）

AI 在对话中可**自主决定**调用 `searchKnowledge` 工具检索站内文章并引用。

> **演进记录（一个由实测驱动的重构）**
>
> 最初该工具用数据库 `LIKE` 关键词匹配，实测发现**命中率为 0**：
> 用户说「失眠」，而文章标题是《改善睡眠质量的五个习惯》——字面重合度为 0，
> 这就是检索中的**词汇鸿沟（vocabulary gap）**。
>
> 改用向量语义检索后，实测「失眠睡不着怎么办」与《改善睡眠质量的五个习惯》
> 相似度 **0.618**，正确命中且排序合理。
>
> 值得一提的是：**本次改造只替换了工具内部的检索实现，工具的名称、参数、描述均未变动，
> 对话链路一行未改**——这正是把检索封装为工具而非写死在对话流程中的价值。

- 向量存储复用已有的 Redis（`kb:vec:{id}` / `kb:meta:{id}`），应用层算余弦相似度。
  几十篇规模下延迟毫秒级，**不引入独立向量数据库**，避免过度设计。
- 按相似度阈值（0.35）过滤噪声，避免把不相关文章硬塞给模型导致生搬硬套。
- 增量同步：文章发布/下线/修改/删除时自动重建或移除索引，
  **保证文章下架后 AI 立即无法再引用**。

**三级降级链**：单一检索手段不可靠——向量检索依赖外部 Embedding 服务，
抖动、限流、网络异常都会导致不可用。

```
① 向量语义检索（主）
     ↓ 服务异常，或结果为空 / 全部低于相似度阈值
② 关键词检索（MySQL LIKE）
     ↓ 仍无结果
③ 明确告知「无相关依据」，禁止编造
```

- 第 ③ 级按**是否受限话题**分流：普通话题允许模型凭自身知识回答；
  受限话题**直接返回预置安全话术**，不交给模型（那正是最容易被「贴心编造」的地方）。
- 未引入 BM25：知识库规模只有几十篇，为它维护倒排索引属于过度设计，
  而 LIKE 在中文短文本上的表现与 BM25 差距很小。
- Embedding 调用失败会记录 **error 级日志**：否则服务不可用会表现为
  「检索效果莫名变差」，运维侧看不出根因。
- 结果附带**文章阅读链接**（Markdown 格式），前端渲染为可点击锚点，用户可直接跳转全文。

### 异步架构（RabbitMQ）

文章的向量化需要调用 Embedding 接口，**耗时且可能失败**（实测在批量导入时曾因限流
触发 `Connection reset`，导致个别文章漏建索引）。因此改为消息队列异步处理：

```
发布文章 → 立即返回响应
            ↓（投递消息）
     knowledge.index.queue → 消费者 → 调用 Embedding → 写入 Redis
                                  ↓ 重试 3 次仍失败
                        knowledge.index.dlq（死信队列，保留现场）
```

**可靠性设计**

| 机制 | 做法 | 解决的问题 |
|---|---|---|
| 手动 ACK | 处理成功才确认 | 避免「已确认但实际没成功」导致索引缺失 |
| 重试计数 | 手动重投并递增 `x-retry-count` 头 | 不用 `NACK + requeue`，因为重新入队不改变消息头，计数无法递增，会变成无限重投 |
| 死信队列 | 重试耗尽后 NACK 入 DLQ | 失败消息**保留现场**而非静默丢弃 |
| 幂等 | 消费者回查数据库最新状态 | 同一文章多条消息**乱序到达也能收敛到一致结果** |
| `prefetch=1` | 串行消费 | 天然形成对 Embedding 接口的限流保护 |

**启动对账兜底**：服务启动时会扫描「已发布且可引用」的文章，比对 Redis，
缺失的自动补建（逐篇间隔 150ms 防限流），保证消息丢失后索引仍能最终一致。

### 用户投稿与审核（内容治理）

用户可投稿心理科普内容，经管理员审核后决定是否展示、以及是否允许被 AI 引用。

**核心设计：`citable` 与 `status` 解耦**

> 「能被读者看到」与「能被 AI 当作专业依据引用」是两件事。

心理健康场景下，用户分享的个人经验可以展示给读者，但**不适合被 AI 作为权威建议
转述给另一个处于痛苦中的用户**。因此：

| 字段 | 含义 |
|---|---|
| `status` | 内容对读者是否可见（0草稿/1已发布/2已下线/3待审核/4已驳回） |
| `citable` | 内容能否进入 AI 知识库被引用（**与 status 独立**） |

用户投稿默认 `citable=0`，授权 AI 引用必须是**审核人的显式动作**，不靠默认值放开。

- 只有 `status=1 且 citable=1` 的文章才会被向量化进 AI 知识库。
- 审核接口与投稿接口使用**独立路径前缀**（`/api/knowledge/review`、`/api/knowledge/submission`），
  避免被 `SecurityConfig` 中针对 `/api/knowledge/article/*` 的公开 GET 规则意外放行造成越权。

### 数据看板

后台首页展示用户、情绪日志、咨询会话的统计与近 7 天趋势。

- 趋势数据**补齐没有数据的日期**，否则折线图会跳过空缺日期导致时间轴失真。
- 会话内的消息**一次性查出后在内存分组**，避免逐个会话查询造成的 N+1 问题。

### 前端设计系统（雾蓝主题）

各页面原先直接写死色值，累计出现 40 余个零散颜色（青绿、橙、蓝混用），
视觉上不像一个产品。现统一到 `src/styles/theme.css`：

- 定义 29 个设计 token（主色阶、语义色、中性色、圆角、阴影、渐变），
  页面只引用变量、不再写死色值，换肤只需改一处。
- 覆盖 Element Plus 主题变量（`--el-color-primary` 及其浅色阶），
  使组件库与自定义样式配色一致。

> ⚠️ `theme.css` **必须在 `element-plus/dist/index.css` 之后导入**，
> 否则主题变量会被组件库默认值覆盖。

**配色依据**：心理健康产品的用户常处于焦虑、失眠状态。色彩心理学上，暖色与高饱和色
会**提高生理唤起水平**，反而加重不安；低饱和冷色能降低唤起、传递平静与安全感。
因此主色选用低饱和雾蓝（`#5c8db8`），仅风险提示保留暖色以示警。

其他细节：情绪分值圆环按情绪水平变色（积极青绿 / 中性雾蓝 / 低落冷紫）；
支持 `prefers-reduced-motion`，系统开启「减少动态效果」时自动关闭动画。

## 四、已知限制

这些是当前实现中有意识做出的取舍，也是后续可演进的方向：

1. **管理员与前台互斥**：路由守卫按 `userType` 排他，管理员账号无法访问前台页面。
   要同时体验投稿与审核，需使用**两个浏览器上下文**（如普通窗口 + 无痕窗口），
   因为 token 存于 `localStorage`，同浏览器多标签会互相覆盖。

2. **审核权绑定管理员角色**：`roleType==2` 代表管理权限，**不等同于心理专业资质**。
   生产环境应引入独立的「专业审核人」角色，而非复用系统管理员。

3. **检索规模上限**：当前向量检索在应用层做全量余弦计算，适合几十到数百篇。
   若文章涨到数万篇，需换成 Redis 向量索引或专用向量库——
   `KnowledgeVectorStore` 对外接口无需变动。

4. **通知未做实时推送**：目前站内信靠前端 30 秒轮询，**没有 WebSocket 推送**。
   对危机场景而言，秒级触达更理想，后续可接入 WebSocket 或服务端推送。

5. **邮件渠道默认未启用**：需要自行配置 SMTP 才能生效，
   未配置时自动降级为「仅站内信」。

6. **辅导员可见全部学生**：这是简化实现。情绪日记正文、对话内容都是极度敏感的数据，
   生产环境应按**分管范围**隔离（例如辅导员只看有未闭环工单的学生），
   相关扩展点在 `ConsultationSessionService.listAllSessions` 的注释中标明。

7. **平均会话时长口径**：项目未记录会话结束事件，用「最后一条消息时间」近似，
   长时间挂着不说话的会话会拉高平均值。

8. **死信队列无自动补偿**：索引消息重试 3 次仍失败会进入 `knowledge.index.dlq`
   保留现场，但目前**没有自动重放机制**，需要人工介入处理。
   生产环境可加定时任务或管理接口来重放死信消息。

9. **Agent 轨迹未做「思考步骤」**：真实 ReAct 轨迹包含显式的 Thought 文本。
   本项目的对话模型未被要求输出思考过程（强制输出会污染用户可见的回复），
   因此轨迹只记录客观发生的事实：轮次开始、工具调用、内容生成、安全拦截——
   这三者已构成完整的 Action → Observation → Response 链路。

## 五、安全提示

- **所有密钥通过环境变量注入**。`application.yml` 中仅保留 `${VAR:默认值}` 形式，
  默认值均为面向本地开发的非敏感值，不含任何真实凭证。
- `JWT_SECRET` 与数据库密码**在生产环境必须显式配置**，不要依赖配置文件中的默认值。
- **建议定期轮换** DeepSeek 与阿里云百炼的 API Key；Key 一旦泄露可被他人消耗额度。
- `.m2` 离线构建环境下 `mvn test` 可能因缺少 surefire 插件而失败，需联网拉取依赖。
- 当前项目**几乎没有单元测试**（仅一个脚手架测试），这是已知的工程短板。
